I took the most popular tracking algorithm, made it compute the math for all cameras in shared GPU batches — and stepped on three rakes along the way that anyone writing real-time PyTorch pipelines should know about.

The problem: N cameras = N trackers = a sad CPU

A typical production video-analytics setup: one GPU server, 8–32 RTSP streams coming in, YOLO detecting people/vehicles on every frame — and then you need tracking: stable object IDs from frame to frame.

Detection is fine: YOLO batches beautifully, 16 frames go through one inference call. Then it gets interesting. Every popular Python tracking library — BoxMOT, Norfair, roboflow/trackers, the tracker built into ultralytics — is built the same way: one tracker instance per video stream, all math on the CPU. The official recipe for multiple cameras is "wrap each camera in its own thread/process."

That works at 2–4 cameras. At 16, the Kalman filters, IoU matrices and track bookkeeping eat your cores faster than YOLO can detect: in our measurements, 16 streams of CPU ByteTrack cost 104 ms per frame — against 6 ms for detection. The tracker that's supposed to be "lighter than the detector" becomes the pipeline bottleneck.

The only solution with true cross-camera batching is NVIDIA DeepStream (nvtracker). But that means a GStreamer pipeline, C++ plugins, YAML configs and a closed-source tracker core — a different weight class entirely if your whole pipeline is Python. (Detailed comparison at the end.)

I wanted a third option: DeepStream-grade efficiency, but pip install and three files of PyTorch. That's how BatchGpuByteTrack came to be.

The idea: a tracker as a batched operation

The key observation: ByteTrack's math batches just as well as a neural network does.

  • Kalman predict/update — small matrix multiplications (8×8). A thousand tracks is a [1000, 8, 8] tensor: one torch.einsum call instead of a thousand numpy calls.
  • IoU cost matrices — pairwise box intersections. All streams pack into one padded tensor [S, M_max, N_max] — a single kernel.
  • ReID embeddings — detection crops from all cameras go into one OSNet batch.

What stays on the CPU is what genuinely belongs there: the Hungarian algorithm (lap.lapjv solves tens-by-tens matrices in microseconds — GPU LAP solvers pay off at millions of variables, not at our sizes) and track lifecycle management.

The resulting pipeline: one batched GPU phase (predict + IoU + OSNet) → one bulk download to CPU → per-stream parallel association → one batched GPU phase (update). All CPU↔︎GPU traffic is a fixed number of bulk copies per frame, independent of camera count.

And the algorithm is faithful ByteTrack: the full three-stage association (including the signature "BYTE" recovery of low-confidence detections), a confirmation stage for new tracks, the same thresholds. Parity with the reference implementation is pinned down by tests.

Then came the rakes

The first version worked, but the profiler showed something odd: at 16 streams, the GPU version beat the CPU by only 1.2x. The investigation turned into three separate stories.

Rake #1: "batched" code with a per-stream loop

A classic. Kalman predict was already batched — one operation for all tracks of all cameras. Kalman update was not:

# before: each stream pays its own upload, kernel, and download
for stream_id in range(num_streams):
    means, covs, meas = collect_matched(stream_id)          # CPU
    means_t = torch.from_numpy(means).to(device)            # upload ×16
    upd_means, upd_covs = kalman.batch_update(means_t, ...) # kernel ×16
    results[stream_id] = upd_means.cpu().numpy()            # download ×16

Sixteen streams — 48 tiny GPU operations per frame. Each is microseconds of useful work wrapped in tens of microseconds of overhead: kernel launch, synchronization, a PCIe transaction.

The fix is trivial — gather the matched pairs of all streams into one tensor:

# after: one upload, one kernel, one download — for all streams
entries, means, covs, meas = collect_matched_all_streams()
upd_means, upd_covs = kalman.batch_update(stack(means), stack(covs), stack(meas))
scatter_back(entries, upd_means.cpu().numpy())

The stage dropped from 11.8 ms to 1.6 ms. The same trick for IoU matrices (a padded [S, M_max, N_max] batch instead of a loop) shaved another 5 ms:

The moral: if your "GPU-accelerated" code has a for loop over streams/objects with .to(device) inside, it's not GPU code — it's an overhead generator.

Rake #2: uploading frames at 1.6 GB/s on a 25 GB/s bus

ReID needs the frames on the GPU. Micro-profiling showed: uploading 16 frames of 720p (44 MB) took 26.7 ms — that's 1.6 GB/s on a PCIe 4.0 link capable of ~25.

The culprit is pageable memory: a plain torch.from_numpy(arr).to('cuda') from a numpy array goes through the driver's intermediate staging buffer. The cure is a persistent pinned buffer of your own:

buf = torch.empty(F, H, W, 3, dtype=torch.uint8, pin_memory=True)  # once
...
for i, frame in enumerate(frames):                       # every frame
    buf[i].copy_(torch.from_numpy(frame))                # memcpy into pinned
imgs = buf.to(device, non_blocking=True)                 # DMA at full speed

While at it, all detection crops are now cut and resized in a single torchvision.ops.roi_align call over the uploaded frames — instead of a per-detection "cut crop → upload → resize" loop (the same anti-pattern as rake #1, just with images).

Rake #3: FP16 and 300 milliseconds per new batch size

The sneakiest one. We enabled FP16 inference for OSNet (embeddings tolerate it fine, 2x speed) — and test runs started showing inexplicable freezes: median feature extraction at 14 ms, but regular 300 ms frames.

It turned out: cuDNN selects kernels per input shape, and under FP16 that selection costs ~300 ms for every NEW batch size. And the batch size is the number of detections in the frame — it changes every frame: 48 crops, 52, 47, 61... Every new number is a new freeze. Under FP32 the same warmup costs ~40 ms, which is why nobody notices it there.

The cure is bucketing: pad the inference batch to a multiple of 32 (drop the extra rows afterwards). The number of distinct shapes collapses to 3–4 per run, each warmed once — or all pre-warmed at initialization:

If you have a PyTorch model in production receiving variable-sized input under autocast — check your p99 latency. You might be paying this tax right now.

End-to-end with real YOLO on pedestrian video (8 streams): tracking at 5.1 ms vs 31.8 ms on CPU (6.2x); with detection included — 91 FPS for a batch of 8 cameras.

At 1–2 cameras the CPU wins: the GPU's fixed overhead doesn't pay off there.

ReID

ReID changes the picture: 70–80% of the frame is OSNet inference — irreducible compute. Batched roi_align + pinned buffers + FP16 made feature extraction ~2.3x faster:

But no miracles: with ReID, the overall GPU-over-CPU win is 1.8x at 8 streams (Amdahl's law — both sides pay comparably for the network while crop counts are small). Beyond that, either reid_interval (features every K-th frame — tracks live on smoothed embeddings in between) or TensorRT, which is on the roadmap.

What did NOT work (and why it's in the repo)

  • Batched LAPJV for the Hungarian step — parallelizing the solve of tiny matrices is pointless; thread overhead exceeds the solve.
  • torch.compile kernel fusion — dynamic shapes (track counts change every frame) trigger recompilations that eat the entire gain. We'll revisit after moving Kalman state into resident GPU tensors (which makes shapes static).
  • Hungarian on GPU — GPU LAP implementations pay off from millions of variables; our matrices are tens-by-tens.

All three dead ends are documented in docs/optimization_guide.md.

Comparison with NVIDIA DeepStream (nvtracker)

The only serious counterpart in terms of cross-camera batching. A point-by-point comparison:

DeepStream nvtracker BatchGpuByteTrack
Algorithms IOU, NvSORT, NvDeepSORT, NvDCF, MaskTracker (SAM2) ByteTrack (+ OSNet ReID)
Stream batching Yes, all streams in one call Yes, all streams in shared GPU batches
Integration GStreamer pipeline, C++ plugin, YAML configs pip install, ~10 lines of Python
Detector Inside the DeepStream pipeline (nvinfer) Any: numpy [N, 5] in
Platform NVIDIA dGPU / Jetson + the DeepStream stack Any CUDA GPU + PyTorch; CPU mode included
ReID TensorRT models OSNet (FP16), or your own embeddings via the API
Openness Plugin source available; tracker core is a closed binary 100% open source, MIT
What we lack NvDCF (visual tracking between detections), 3D multi-view, sub-batching, PVA on Jetson —

Bottom line: if you already live in the DeepStream ecosystem, or you need NvDCF / Jetson specifics — take nvtracker, it's more mature. If your pipeline is Python/PyTorch, your detector is your own, and you want to read and modify your tracker's code — that's what BatchGpuByteTrack is for.
